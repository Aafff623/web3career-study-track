## 一、学员心得分享

### 1. 尤娜老师：两个让 AI 输出质量提升的提示词

很多人用 AI 的方式太粗糙，只是直接输入"帮我写文案""帮我做方案"，但 AI 并不了解使用者的职业、行业、客户、业务目标和真实痛点，输出结果往往是"通用但没针对性"的标准答案。她建议把 AI 训练成长期了解自己的专属助理，而不是每次都从零开始提问。

#### 提示词一：让 AI 先全面了解你

```
我想让你全面了解我。
- 我的职业是什么？
- 我所在的公司的核心业务是什么？
- 我的主要客户是谁？
- 现在请你向我连续提问，直到你完全理解我的业务目标、客户群体、工作场景，以及我目前最真实的痛点。
```

使用方法：不要急着让 AI 直接输出方案，先认真回答 AI 提出的每一个问题。回答越具体，AI 越能理解你的真实业务背景。这个过程认真做一次后，可以长期复用。

> *这里的重点不是"提示词神奇"，而是先建立上下文。AI 的输出质量，很大程度取决于它是否知道你是谁、你在解决什么问题。*

#### 提示词二：让 AI 成为"挑刺型陪练"

```
基于你目前对我的了解，从现在开始，请你成为我的专属陪练。
以后不管我提出什么想法，你第一反应都不要夸我，而是先帮我找问题。
请列出 3-5 个我可能忽略的风险、漏洞、反面观点或者关键盲区。
```

适用场景：写商业方案、做产品设计、写内容选题、做决策判断、检查项目逻辑、发现用户视角下的盲区。

很多时候我们需要的不是一个只会说"你很棒"的 AI，而是一个能指出问题的对手。尤其在方案、产品和商业决策中，挑刺型 AI 往往比单纯夸奖型 AI 更有价值。

#### 长期对话的小技巧

如果使用 ChatGPT，可以把这个对话放进 Project；如果使用其他 AI 工具，也可以固定一个长期对话。之后有新的想法、方案或文案需求，都继续在这个上下文里交流。AI 不用每次重新认识你，会越来越理解你的业务，输出会越来越像一个真正熟悉你的数字助理。

> *这其实是在搭一个"个人上下文资产"。与其收藏一堆零散提示词，不如先把自己的业务背景沉淀成可持续复用的 AI 记忆。*

### 2. 花花老师：AI Agent 的第一步不是聊天，而是被授权地做事

花花老师本周把主方向收敛到 **DeFi / Agent Workflow**，重点关注 AI Agent 与 Web3 结合时的真实系统问题。她认为，AI x Web3 最有意思的交集，不是给 DApp 加一个聊天框，而是让 Agent 拥有身份、权限、支付能力、可追责的行动记录。

核心问题是：当 Agent 真的开始替人行动，比如调用付费 API、购买分析结果、准备链上交互时，它到底有没有被授权？预算是多少？超预算时由谁确认？如果判断错误，最后由谁负责？

#### 四个关键维度

| 维度 | 需要回答的问题 |
|------|--------------|
| 授权 | Agent 的请求是否代表用户真实意图？是谁给了支付权限？ |
| 预算 | 支付金额、支付对象、时间窗口、使用次数如何限制？ |
| 责任 | 买错、超预算、结果异常时，系统能否说明是谁下单、谁授权？ |
| 结论 | 难点不在支付通道，而在授权、控制、追责的完整闭环。 |

> *花花老师把问题从"Agent 能不能付款"推进到了"Agent 凭什么可以付款"。这是 AI Agent 商业化和链上化必须面对的问题。*

#### x402 与受控支付的理解

x402 可以理解为一种让 Agent 为资源付费的机制：

1. Agent 请求一个付费 API
2. 服务端不直接返回数据
3. 服务端返回 `402 Payment Required`
4. 返回本次访问价格、收款方等信息
5. Agent 处理支付
6. 支付成功后，服务端再返回真正结果

| 模块 | 作用 |
|------|------|
| x402 | 解决"怎么付"的入口问题 |
| Cobo / MPC / Policy Control | 限制钱在什么范围内可以被花 |
| 审计记录 | 解决事后追责与解释问题 |

#### 项目构想：Agent Pay Guard

场景设定：有一个电商分析 API 是付费的；用户先给 Agent 一个很小的预算（例如 0.1 USDC）；Agent 调用 API 时，如果服务端返回 `402 Payment Required`，系统检查价格是否在预算内——在预算内则通过受限钱包完成支付，超出预算则请求人工确认。支付完成后，前端展示本次调用花了多少钱、拿到了什么结果、为什么这次支付被允许、审计记录是什么。

```mermaid
flowchart TD
    A[用户授权 Agent] --> B[设置预算上限]
    B --> C[Agent 发起 API 请求]
    C --> D{服务端返回 402?}
    D -- 是 --> E{价格在预算内?}
    D -- 否 --> F[正常返回数据]
    E -- 是 --> G[受限钱包完成支付]
    E -- 否 --> H[请求人工确认]
    G --> I[服务端返回数据]
    H -->|确认| G
    H -->|拒绝 --> J[中止请求]
    G --> K[审计记录 + 前端展示]
    I --> K
```

> *这个 demo 的亮点不是"自动付款"，而是把 Agent 的权限控制、预算控制和审计记录串成一个闭环。它更像是 Agent 时代的支付安全中间层。*

### 3. ANONYA 老师：Harness Engineering 学习与实操

ANONYA 老师分享了对 Harness Engineering 的学习过程，参考资料来自 GitHub 上与 Claude Code 学习相关的项目。她的理解是：现在大家的关注点正在从"开发 Agent"逐步转向"开发 Harness"。Harness 可以理解为给 Agent 提供工具、环境、约束和领域引导的工程结构。

#### Harness 的作用

Harness 会根据不同领域变化，帮助 Agent 进入更具体的业务场景。它使 Agent 不只是一个聊天工具，而是能在不同领域里调用工具、执行任务、纠错和适配。可能扩展到的领域包括商学、农学、医学、软件开发、垂直行业应用等。

> *如果说 Agent 是"会思考和调用工具的执行体"，Harness 更像是它进入真实工作场景所需要的轨道、护栏和工具箱。*

#### 实操流程概览

ANONYA 老师目前主要在 macOS 环境下尝试，大致流程：

1. 安装 Python 依赖
2. 配置 API Key
3. 填入 Model ID 和 Base URL
4. 保存配置
5. 进入 S01 Agent Loop
6. 运行测试任务
7. 观察 Agent 的错误恢复能力
8. 进入 S02，给 AI 增加更多工具
9. 继续测试读文件、改文件、查找文件等任务

#### S01：Agent Loop 与基础纠错

S01 阶段主要观察 Agent 在任务循环中的表现：尝试读取文件、创建文件、遇到错误后重新修复、自动调整执行路径。

#### S02：给 AI 更多工具

S02 阶段增加 `read_file`、`edit_file`、`bash`、`glob` 等工具，让 Agent 不只生成文本，而是更接近真实开发环境中的执行者。

#### 复杂任务中的错误恢复案例

一个典型流程：Agent 先尝试读取 README → 成功 → 再尝试读取 requirements → 发现文件不在当前路径 → 使用 glob 查找 → glob 出现 bug → 改用 bash 查找 → 找到文件后尝试用 read_file 读取绝对路径 → 发现被 sandbox 拦截 → 再尝试读取相对路径 → 仍然失败 → 最后用 bash cat 读取 → 输出 summary → 任务结束。

> *这段最值得注意的是"失败后的路径切换"。一个有用的 Agent 不应只是在理想条件下完成任务，而要能在工具失败、路径错误、沙箱限制下继续寻找替代方案。*
