# Context ｜ 上下文

*约 1800 字 · 6 分钟 · 2026-05-12*

---

Context 是模型在一次推理中能"看到"的全部信息。它决定了模型知道什么、不知道什么，以及它的回答能走多远。Context 管理不好，模型要么遗漏关键信息，要么被无关内容淹没，要么因为窗口不够而丢失重要上下文。

## 为什么要学这个

很多 AI 应用的问题不是模型不够强，而是模型"看错了东西"。要么该给的没给，要么给得太多太杂，要么给了过时的、错误的、甚至被污染的内容。Context 管理的核心就是决定：在有限的上下文窗口里，放什么、不放什么、怎么放。

> *Context 是模型的"视野"，放什么进去直接决定模型的输出质量。窗口是有限的，放错东西比不放更危险。*

## 第一性原理

**Context 的质量决定输出的上限，窗口大小只是约束条件。**

上下文窗口是有限的，但"有限"不是最大的问题——最大的问题是放进去了不该放的东西。无关文档会稀释注意力，过时信息会误导判断，恶意内容会劫持模型行为。

- **按相关性排序，不按时间排序**：最近的不一定是最重要的，最相关的才是。
- **按来源可信度标记**：链上数据、项目文档、用户输入、检索结果的可信度完全不同，模型和代码都需要知道这一点。
- **按敏感度分层**：公开信息、内部数据、私钥和签名权限必须分开处理，不能混在同一个上下文里。

> *Context 管理不是"塞更多信息"，而是"精准选择该放什么"。在 AI×Web3 里，一条错误的交易数据比十条无关文档更有害。*

## 知识节点


### System Prompt

System Prompt 是在对话开始前注入的角色定义和行为规则。它告诉模型：你是谁、能做什么、不能做什么、遇到不确定情况怎么处理。

好的 System Prompt 要区分三个层次：身份（你是一个交易风险分析师）、能力（你能解释交易、标记风险、列出不确定性）、边界（你不能替用户确认交易、不能编造不存在的数据）。

> *System Prompt 是模型的"底色"——它定义了模型看所有后续信息时的视角和边界。没有清晰的 System Prompt，后面的 Context 塞得再精准也容易偏离。*


### User Message

User Message 是用户在对话中实际说的话或提供的信息。它是模型推理的直接触发器，但模型不会只看这一条——它会结合 System Prompt 和整个上下文来理解用户意图。

User Message 的质量直接影响模型输出。模糊的指令会得到模糊的回答，具体的指令会得到具体的输出。工程上要关注的不是"怎么让模型猜对用户意图"，而是"怎么让用户输入更结构化"。

> *User Message 是模型和用户之间的直接接口。不要指望模型"猜"用户想要什么——好的产品设计是让用户更容易说清楚自己要什么。*


### Memory

Memory 是跨对话或跨会话保留的信息。它让模型在多轮交互中"记住"之前的上下文、用户偏好、历史决策和未完成的任务。

Memory 有两种常见形态：短期记忆（同一会话内的上下文延续）和长期记忆（跨会话的持久化存储）。短期记忆通常靠上下文窗口自然承载，长期记忆需要外部存储（数据库、向量库、KV 存储）配合检索系统。

> *Memory 解决的是"模型如何记住"的问题。在 AI×Web3 里，用户的授权记录、交易历史、偏好设置都需要通过 Memory 机制持久化，而不是每次都重新输入。*


### Knowledge Base

Knowledge Base 是专门为模型提供的结构化参考资料。它可以是项目文档、合约 ABI、API 规范、FAQ、历史日志或任何模型需要参考但不在训练数据中的信息。

Knowledge Base 的核心挑战是两件事：**来源**和**时效性**。模型需要知道"这条信息从哪里来"（来源），也需要知道"这条信息还是不是最新的"（时效性）。没有来源标记的信息，模型无法判断可信度；没有时效性管理的信息，模型可能引用过期数据。

> *Knowledge Base 不是"把文档全扔给模型"。在 AI×Web3 里，合约版本在变、协议在升级、API 在改——Knowledge Base 必须有来源追溯和更新机制，否则模型会拿旧版本的信息来回答新版本的问题。*


### Tool Output

Tool Output 是模型调用外部工具后拿到的返回结果。它可能是 API 响应、数据库查询结果、链上数据、模拟执行结果或任何外部系统的输出。

Tool Output 的关键挑战是：模型需要区分"工具返回的事实"和"模型自己的推断"。链上数据是确定的，但模型对数据的解释是推测性的。好的系统要在输出中明确标注哪些是工具返回的原始数据，哪些是模型的推理。

> *Tool Output 是模型接触外部世界的通道。在 AI×Web3 里，链上数据、模拟结果、预言机价格都是 Tool Output——模型可以把它们作为推理依据，但不能把它们和自己的推断混为一谈。*


### Context Window

Context Window 是模型单次推理能处理的信息总量上限。它包括 System Prompt、历史消息、检索结果、工具输出和当前用户输入——所有这些加起来不能超过窗口大小。

Context Window 管理不是"塞更多信息"，而是"在有限空间里放最有价值的东西"。当上下文接近上限时，系统需要决定：丢弃哪些旧消息、压缩哪些中间结果、优先保留哪些关键信息。

> *Context Window 是硬约束——不管你的任务多重要，超出窗口的信息模型根本看不到。在 AI×Web3 里，一笔复杂交易的完整数据（ABI、事件日志、模拟结果、历史上下文）很容易超出窗口，所以必须做取舍。*

## 在 AI x Web3 中的位置

Context 处在数据层和模型之间。它决定了模型能看到什么数据、以什么顺序看到、数据的可信度如何标记。

一条完整的 Context 链路通常是：

1. System Prompt 定义角色和边界
2. Knowledge Base 提供可信参考资料（带来源标记）
3. Tool Output 带回链上数据和外部信息
4. User Message 表达当前意图
5. Memory 保留跨会话的历史上下文
6. Context Window 控制总量，做取舍

> *这条链路的核心判断：模型看到的每一项信息都应该有明确的来源和可信度标记。在 AI×Web3 里，链上数据、预言机数据、用户输入、检索文档的可信度差异很大，混在一起不标注等于让模型自己猜。*

## 最小实践

做一个"钱包授权检查"助手。

用户输入一个授权交易的数据（目标地址、授权额度、函数签名），系统需要：

1. 通过工具读取链上数据（目标合约类型、历史交互记录）
2. 从 Knowledge Base 检索项目文档（该合约的安全信息）
3. 在 Context 中明确标注：哪些是链上事实、哪些是文档信息、哪些是模型推断
4. 输出结构化结果：授权详情、风险评估、不确定性列表

> *这个练习的核心：不是让模型"回答得好"，而是让 Context 中的每一项信息都有清晰的来源和可信度边界。模型输出必须区分"链上事实""文档信息"和"模型推断"。*
