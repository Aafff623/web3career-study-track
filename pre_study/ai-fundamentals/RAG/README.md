# RAG ｜ 检索增强生成

> 模块：AI 基础 · 状态：🟡 整理中 · 来源：AI Web3 School Handbook

*约 1950 字 · 6 分钟 · 2026-05-12*

---

RAG 是把"检索"和"生成"组合在一起的架构模式。模型先从外部数据源找到相关资料，再基于这些资料生成回答。它解决的核心问题是：模型训练数据有时效性限制，RAG 让模型能引用最新的、特定领域的、私有的信息。

## 为什么要学这个

LLM 的训练数据是静态的——它不知道今天的链上发生了什么，没读过你项目的最新文档，也不了解刚升级的合约接口。如果只靠模型自身的知识，它要么拒绝回答，要么编造答案。

RAG 的价值在于：不改模型，只改模型能看到的信息。通过检索系统把相关文档、数据或上下文喂给模型，让它基于真实资料生成回答。这样既保留了模型的推理能力，又弥补了知识时效性的短板。

> *RAG 的核心价值是让模型"有据可依"，而不是"凭空想象"。在 AI×Web3 里，协议文档在变、合约在升级、提案在推进——没有 RAG，模型只能靠过期的训练数据猜。*

## 第一性原理

**RAG 的本质是"先找后答"，检索质量决定生成质量。**

模型生成的内容质量上限由检索回来的资料决定。如果检索结果不相关、不准确或不完整，模型再强也只会"一本正经地胡说八道"。RAG 系统的关键不在生成端，而在检索端。

- **Chunking 粒度要匹配任务**：按段落切适合问答，按句子切适合精确匹配，按文档切适合摘要。切得太细会丢失上下文，切得太粗会稀释相关性。
- **Embedding 要和查询类型匹配**：语义搜索用 embedding，关键词搜索用 BM25，混合检索通常效果最好。
- **检索结果要排序和过滤**：不是所有检索结果都值得放进上下文，需要根据相关性、来源可信度和时效性做筛选。

> *RAG 不是"搜到什么就给模型看什么"。检索回来的资料需要经过排序、过滤和可信度标记，否则模型会被低质量检索结果误导。*

## 知识节点


### Chunking（分块）

Chunking 是把长文档切成适合检索和注入的小片段。切分方式直接影响检索质量：切得太小会丢失上下文，切得太大会稀释相关性。

常见切分策略有：固定长度切分（按字符或 token 数）、语义切分（按段落或主题边界）、结构化切分（按文档结构如标题、章节）。

> *Chunking 的核心是"在不丢失关键上下文的前提下，把信息切成可检索的单元"。没有一刀切的最佳方案，切分策略要跟任务类型匹配。*


### Embedding（向量化）

Embedding 是把文本片段映射成向量，用来衡量语义相似度。在 RAG 中，它负责把查询和文档片段都转成向量，然后通过向量相似度找到最相关的片段。

Embedding 的局限是：它只能衡量"语义上接近"，不能判断"事实上正确"。两个语义相似的片段可能表达的是矛盾的观点，或者一个已经过时。所以检索回来的结果还需要排序和校验。

> *Embedding 解决的是"找到语义相关的内容"，但不解决"找到的内容是否正确"。在 AI×Web3 里，旧版本的合约文档和新版本可能语义相似但含义完全不同。*


### Vector Store（向量数据库）

Vector Store 是存储和检索向量的专用数据库。它支持高效的相似度搜索，是 RAG 检索端的核心基础设施。

常见选择有 Pinecone、Weaviate、Chroma、pgvector 等。选型时需要考虑：数据规模、查询延迟、过滤能力、与现有系统的集成难度。

> *Vector Store 是 RAG 的"记忆仓库"——它让检索系统能快速找到相关片段。选型时不要只看性能指标，还要看是否支持元数据过滤和来源标记。*


### Retrieval（检索）

Retrieval 是根据用户查询，从 Vector Store 中找到最相关的文档片段的过程。简单的做法是纯向量搜索，更稳的做法是混合检索（向量 + 关键词）加重排序。

检索质量直接决定 RAG 的上限。如果检索回来的资料不相关，模型生成的内容必然偏差。所以 RAG 系统的优化重点通常在检索端，而不是生成端。

> *Retrieval 是 RAG 链路中最关键的环节。模型生成的质量上限由检索结果决定——检索错了，后面全白搭。*


### Generation（生成）

Generation 是模型基于检索回来的资料，结合用户查询，生成最终回答的过程。好的 RAG 系统要让模型"引用"检索结果，而不是"无视"它们。

模型在生成时需要做几个判断：哪些检索结果和查询相关、哪些信息可以直接引用、哪些地方资料不足需要说不知道。这些判断的质量取决于 System Prompt 的设计和检索结果的质量。

> *Generation 不是"把检索结果拼起来"，而是"基于检索结果做推理和组织"。模型需要有能力判断哪些资料值得引用、哪些地方需要补充说明。*


### Citation（引用）

Citation 是在模型输出中标注信息来源的做法。它让用户能验证模型回答的依据，也方便系统做来源追溯和可信度评估。

好的 Citation 要做到：标注具体来源（不是"根据文档"，而是"根据 X 文档第 Y 节"）、区分直接引用和模型推断、标注信息的时效性。

> *Citation 是 RAG 系统可信度的关键。没有来源标注的回答只是"模型的意见"，有了 Citation 才是"基于证据的推理"。在 AI×Web3 里，链上数据和文档版本都需要精确溯源。*

## 在 AI x Web3 中的位置

RAG 在 AI×Web3 系统中负责让模型接触到最新的、特定领域的、私有的信息。它通常连接这些数据源：

| 数据源 | 用途 |
|--------|------|
| 项目文档 | 协议规范、API 文档、FAQ |
| 合约 ABI | 函数签名、事件定义、参数类型 |
| 提案记录 | Snapshot、Tally、论坛讨论 |
| 链上数据索引 | 交易历史、事件日志、状态变化 |
| 社区知识库 | 治理规则、最佳实践、常见问题 |

> *RAG 是 AI×Web3 系统的"信息桥梁"——它把分散在不同地方的可信信息汇聚到模型面前。关键是每条信息都要带来源标记和时效性标注。*

## 最小实践

做一个"协议文档问答"系统。

输入：用户关于某个 DeFi 协议的问题。

流程：
1. 从协议文档库中检索相关段落（用混合检索：向量 + 关键词）
2. 对检索结果按相关性排序
3. 把排序后的结果注入 Context，让模型生成回答
4. 模型输出必须包含：回答内容、引用来源（具体文档和章节）、不确定的部分

> *这个练习的重点：不是让回答"看起来对"，而是让每一条回答都有可追溯的来源。模型在引用资料时必须区分"文档明确说明的"和"模型基于资料推断的"。*
